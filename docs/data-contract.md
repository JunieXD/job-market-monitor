# 数据契约

本项目的数据层遵循四条不可破坏的原则：

1. 官网事实、系统观测、统一映射和派生结果分层保存。
2. 每一项历史分析都可以还原到某次完整采集和某个岗位版本。
3. 映射、规则和模型升级时保留旧结果，新结果以发布批次切换。
4. 聚合视图可以重建，不能成为唯一事实来源。

## 来源事实层

`JobRecord` 只能保存招聘官网直接公开并已规范化的事实。当前公共字段包括：

- 来源内部 ID 与展示职位编码
- 来源链接、公司和社招/校招渠道
- 正式/实习类型和校招项目
- 原始标题、职位描述和职位要求
- 官网发布时间（来源未提供时为 `NULL`）
- 来源更新时间、来源状态和明确招聘人数（来源提供时）
- 官网直接学历代码/名称、经验年限区间、毕业时间区间、部门和面试地点（来源提供时）
- 零个、一个或多个官网职位分类，以及每项分类的赋值方法
- 热门标记
- 零个、一个或多个工作地点；官网未提供时保留空关系
- 来源直接提供的业务单元（例如阿里 `circleCodeList`/`circleNames`）
- 当页原始 JSON 中对应的岗位对象

来源事实不得被统一分类、关键词规则或 LLM 结果覆盖。

不同官网并不提供完全相同的字段。字节提供展示职位编码、发布时间、热门标记和直接分类；
阿里统一校园入口没有岗位发布时间，但提供来源更新时间、毕业时间范围、面试地点、招聘批次、
官网大类、业务单元和工作城市；淘天社招提供发布时间、更新时间、学历代码和经验年限区间，
但岗位对象本身没有分类。没有提供的值必须为 `NULL` 或空关系，不能用其他字段代替。

阿里的 `modifyTime` 只能进入 `source_updated_at`，不得写入 `published_at`。不得仅因为某个来源
没有字段就编造默认值，也不得把官网未结构化提供的学历、技能等从职位文本中猜测出来写入
来源事实层。未来 LLM 或规则提取只能进入派生层。

## 版本与观测

- `jobs` 保存岗位身份和最新已知内容，唯一键为 `source_id + external_id`。
- `job_versions` 保存每一种标准化内容版本，唯一键为 `job_id + content_hash`。
- `job_observations` 表示某次完整采集看到了某个岗位，并且必须指向当时准确的
  `job_version_id`。
- `job_version_locations` 保存某个岗位版本当时对应的全部地点。
- `job_version_location_cities` 保存每个来源地点派生出的城市级关联；一个原始地点标签可以对应多个
  城市，因此同一个岗位版本和来源地点可以有多条记录。
- `job_version_source_categories` 保存当时的全部来源分类及赋值方法。

`job_version_locations`、`job_version_location_cities` 和 `job_version_source_categories` 同时保存该版本观测时使用的统一维度
映射 ID、映射版本、方法和置信度。后续发布新的当前映射不会改写旧岗位版本；历史分析必须优先使用
这些版本快照字段，而不能直接连接 `is_current` 映射。
- `job_locations` 只用于快速查询岗位的最新地点，不能用于历史分析。

`job_locations` 必须与岗位当前内容哈希对应的 `job_version_locations` 集合完全一致；两边同时为空
是合法状态。质量检查不能为了让城市字段非空而编造“未知城市”。

即使岗位内容从 A 变为 B 后又恢复 A，新的观测仍指向旧的 A 版本，历史顺序由观测表保留。

日常采集不会把完整岗位内容重复写入数据库。标题、描述、要求、地点、分类和业务单元等事实
经过标准化后计算 `content_hash`；内容不变时只新增一条包含岗位、版本和采集批次外键的轻量
观测关系，复用已有 `job_versions`。只有官网事实发生变化时才创建新版本，描述或要求的修改也
会产生 `changed` 生命周期事件。`source_updated_at` 可能在官网无可见内容变化时自行移动，因此
不参与内容哈希，但仍保存在 `jobs` 当前事实中。

## 每日标准快照

`crawl_runs.snapshot_date` 按来源配置的时区计算。每个来源、渠道、自然日只允许一个
`daily_snapshots` 记录。`crawl_runs.absence_authoritative` 记录本次结果是否足以对未出现岗位
做缺失判断：

- 当天最新一次完整且 `absence_authoritative=true` 的成功采集成为标准快照；同日重跑会更新
  `daily_snapshots` 指针，分析始终读取当天最后一次权威结果。
- 当天第一次权威成功采集推进一次缺失和关闭状态；后续重跑可以纠正已重新出现的岗位，
  但不会再次增加缺失次数，避免一天被重复计算为多个生命周期周期。
- 失败或不完整采集永远不能成为标准快照。
- `crawl_runs.status` 明确区分 `success`、`partial` 和 `failed`。`partial` 保存已验证岗位、原始证据
  和结构化问题，但 `complete=false`、`absence_authoritative=false`；`failed` 表示入口、浏览器、
  鉴权或结构等错误导致没有可安全持久化的采集结果。
- 完整遍历仍可能因实时列表在翻页期间变化而不具备“缺失判断权威性”。这类运行保存已观察
  岗位和原始证据，但不占用每日标准快照，不推进 `missing` 或 `closed` 生命周期。
- 某来源和渠道的第一个标准快照标记为基线。
- 基线中的全部岗位是初始存量，不计为当天新增。

调度器正常情况下只运行一次；同日人工补跑用于修正失败或不完整结果，并保留全部运行记录与原始证据。

## 生命周期

`job_lifecycle_events` 持久化以下事件：

- `first_seen`：系统第一次在任意完整采集中看到岗位。
- `changed`：当前内容哈希与上次已知内容不同。
- `enriched`：系统升级来源事实契约后，首次补齐此前未结构化保存的官网字段；这不是官网
  岗位变更，不计入市场变化指标。
- `missing`：第一次在标准快照中缺失。
- `recovered`：尚未确认关闭的岗位重新出现。
- `closed`：达到连续标准快照缺失阈值。
- `reopened`：已确认关闭的岗位重新出现。

`closed.effective_at` 使用第一次缺失时间，`observed_at` 使用达到关闭阈值的确认时间。
岗位重开可以清空 `jobs.closed_at`，但历史关闭事件不可删除。

`job_versions.fact_contract_version` 标识生成该标准化版本时使用的来源事实契约。旧契约首次
升级到新契约时会新建可审计版本，以保留新增的官网分类、业务单元或其他直接字段；事件类型为
`enriched`，而不是 `changed`。同一契约内的后续官网事实变化仍记为 `changed`。

## 分类与地点

官网分类和统一分类不能混用：

- `source_categories` 保存来源自己的稳定分类 ID。
- `job_version_source_categories.assignment_method` 只允许 `direct_field` 或
  `filter_membership`。前者来自岗位对象，后者来自官网公开筛选结果。
- `canonical_categories` 保存项目统一、带版本的分类体系。
- `category_mappings` 保存来源分类到统一分类的版本化映射。

岗位可以没有来源分类，也可以属于多个来源分类。淘天岗位对象的分类字段为空，因此连接器先
完整采集根列表，再逐个执行官网一级分类筛选，把筛选结果中的岗位记为 `filter_membership`；未
进入任何筛选结果的岗位保持“未分类”，不得自动塞进“其他”。

地点同样分层：

- `locations` 保存来源地点编码和名称；`job_version_location_cities` 保存地点对应的城市级派生关系。
- `canonical_locations` 保存跨来源统一地点。
- `source_location_mappings` 保存版本化映射。

来源地点的原始 `locations.name` 不会被覆盖。城市分析和 API 展示使用规范化显示名称：统一全角、空白和大小写；
对“省·城市”、省市连写、城市末尾的“市”、总部/分公司等工作地点后缀，以及明确的行政区后缀进行城市级归一化。
例如“深圳市”“深圳总部”“四川省·成都”都会归到“深圳”或“成都”。省份、区域或全国等没有具体城市的标签不被伪造为城市。
API 同时保留 `source_name` 供追溯；历史快照的自动地点映射也按同一规则归并，人工映射不受影响。

自动地点映射使用规范化后的城市名称作为跨来源身份，不把某个来源可选的国家/省字段放进
身份键。这样阿里只提供“北京”、字节提供“中国大陆/北京/北京”时会落到同一统一城市；更
丰富的国家/省信息只用于补全统一城市展示。自动映射保留方法、版本和置信度，遇到跨国家同名
城市等歧义时必须发布人工映射覆盖，且来源地点原文不会被改写。

每个来源分类最多只能有一条 `is_current = true` 的映射。一个包含多个城市的来源地点可以有多条
当前自动城市映射；`job_version_location_cities` 保存观测时实际使用的版本化城市关联。人工或模型
映射仍优先于自动拆分。

业务单元采用来源事实维度：

- `source_business_units` 保存来源代码、名称及有效时间区间；同一来源代码改名时关闭旧版本并
  新建版本，不覆盖历史名称。
- `job_version_business_units` 保存某个岗位版本当时关联的一个或多个业务单元。
- 岗位版本的 `payload` 也保存规范化后的代码/名称对，原始数组仍在 gzip 快照中保留。

这套维度不是统一 topic 分类。跨来源的业务组织是否属于同一集团或同一业务线，必须另行发布
有版本和证据的映射；在此之前只按来源业务单元统计。

## 派生层

派生能力当前停用。项目没有正式主题词表、主题分类结果或 LLM 提取结果，采集命令、定时任务
和默认分析都不会生成或读取这些数据。数据库只预留可审计的通用结构：

- `derivation_runs` 记录规则、LLM 或人工批次的配置、版本、状态和发布时间。
- `job_topic_mentions` 保存主题、相关度、命中字段、证据和置信度。
- `job_derived_attributes` 保存学历、经验、技能、专业、届次等结构化结果。

任何派生结果都只能关联 `job_version_id`，不得写回或覆盖官网事实。曾用于验证数据链路的
Agent 关键词批次和词表已经退役：历史记录仅用于审计，`is_current = false`，对应主题也不再
处于启用状态，因此不会进入默认查询。

重新启用派生能力前必须先确定并版本化：

- 完整的主题或属性定义、边界和层级
- 标注或模型方法及离线评估标准
- 置信度含义、证据格式和人工复核策略
- 发布、回滚和重新计算规则

只有通过上述约束的成功批次才能设置 `is_current = true` 并进入分析。

## 原始快照

每页原始 JSON 使用 gzip 保存，并在 `raw_snapshots` 记录路径、SHA-256、大小、分片、偏移量和
采集时间。分类字典、业务单元字典等参与规范化的官网条件响应也必须保存。数据库中的标准化
事实可以从原始快照重建，但原始数据不得提交到 Git。

`crawl_run_field_stats` 按运行统计原始岗位对象每个字段的出现、非空、非空集合和 JSON 类型
数量，不保存示例值。它用于发现官网字段消失、类型变化或覆盖率骤降，不能替代原始快照。

## 完整性

任何接口分片总数达到来源已知上限时，该分片都不算完整。连接器应继续使用类别、城市或
其他公开筛选维度拆分；尚未实现安全分片或无法继续拆分时必须终止运行。字节连接器已实现
类别/城市分片，阿里连接器当前以招聘批次分片并在单批次触及 10,000 条时失败。只有完整运行
才可以生成标准快照，只有每日标准快照才可以推进生命周期。部分运行可入库已验证观测，但绝不
用于推断岗位缺失。淘天连接器要求根列表和全部官网一级分类筛选都成功才生成标准快照；任何一部分
分页不完整时保存为部分结果。

`job-market check-schema` 必须确认迁移版本、ORM 模型和分析视图完全一致。
`job-market check-data` 必须满足以下核心不变量：

- 观测、岗位版本和采集运行属于同一岗位、来源与渠道。
- 标准快照引用完整成功运行，发现数等于观测数。
- 每次采集运行都有明确的来源渠道契约，字段覆盖统计行数与发现数一致。
- `job_locations` 与当前岗位版本的地点集合一致；两边同时为空是合法状态。
- 来源分类与岗位属于同一来源，多分类版本的兼容主分类指针必须指向其中一项。
- 每个岗位恰好有一个 `first_seen` 事件。
- 当前岗位哈希一定对应已保存版本。
- 每个来源地点恰好有一条当前统一地点映射。
- 关闭岗位必须同时有首次缺失和关闭时间。

完整指标定义见 [metrics.md](metrics.md)。
