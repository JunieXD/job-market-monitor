# 并发与流量实验记录

本文记录采集器并发和网络优化的实验方法。所有“岗位数”都必须同时满足来源接口的总数、分页行数
和唯一岗位校验；节省流量不能以少抓岗位为代价。

## 调度模型

批次启动时先执行 schema、运行时磁盘、孤儿运行恢复和当天待采集来源检查。随后每个来源进入独立
worker：

1. 同一来源的渠道始终由一个容器串行执行。
2. 不同来源最多同时运行 `MAX_PARALLEL_SOURCES` 个 worker，默认值为 2。
3. 新 worker 默认等待 `SOURCE_START_DELAY_SECONDS=3` 秒，降低启动瞬间的带宽峰值。
4. 每个来源单独超时、重试、恢复和清理；一个失败不会阻止其他来源。
5. 全局 `flock` 防止两个 systemd 批次重叠；`--due-only` 防止重试重新抓取当天已成功渠道。

采集网络并发与数据库写入并发分离。PostgreSQL 事务级 advisory lock 保护共享公司/来源元数据、
维度、岗位生命周期和每日快照指针；浏览器抓取仍然可以并发。SQLite 测试不执行 PostgreSQL
锁语句。

## 流量策略

Playwright 的 `context.route` 会关闭 HTTP 缓存，因此项目使用 Chromium CDP 的 URL 模式阻止常见
图片、字体、音视频扩展名，并阻止 Service Worker。岗位接口、脚本、文档和必要的 XHR/fetch 保留。
连接器内部如有额外的资源策略，仍由统一网络指标记录失败和接收字节。

连接器不再使用 Playwright `page.route` 做同样的图片/字体拦截，因为该 API 会关闭 Chromium HTTP
缓存，导致重复打开详情页时反复下载脚本。统一 CDP 策略保留浏览器缓存，同时阻止非必要资源；
定时调度器会先检查采集镜像，并使用 `docker compose run --pull never`，避免把镜像拉取、构建和
Chromium 安装流量混入每日采集。

Collector 的 Docker 构建上下文也已排除 `frontend`、测试和文档目录；在 Ubuntu 上实测上下文从约
1.39 GiB 降到约 2.65 MiB。这是 Parallels 主机到虚拟机的构建传输优化，不计入招聘网站的每日外网
流量，也不会改变镜像内的采集代码。

CDP 指标包括请求/响应数、接收字节、资源类型分布和失败数。连接器如果使用独立的
`APIRequestContext`，这部分请求不经过页面 CDP，最终实验必须同时记录 Docker `NET I/O`；改用页面内
`fetch` 的连接器则会重新纳入 CDP。原始岗位 JSON 仍按 gzip 快照保存，原始证据不因网络优化删除。

快手首次基线出现“无岗位接口响应”并超时。诊断确认官网脚本正常，原因是 Ubuntu 运行镜像没有包含

快手的初始化资源策略必须在代码、镜像和启动日志中保持一致，采集开始日志现在会记录实际生效的
`resource_policy`。

这次修复没有通过跳过岗位或缩减分页来节省流量。快手仍保留完整页面初始化，后续若要继续降低图片等附属
资源，必须先做“首屏初始化后再拦截”的单独实验，并以岗位数、分页元数据和 `collection_hash` 回归通过为前提。

### 来源级详情接口优化

### 2026-08-20 字节跳动单次 SPA 初始化优化

官网实测确认筛选器可以在同一页面内通过“清除”恢复根状态，再选择分类和城市；不需要重新导航
列表页。连接器现在每个渠道只初始化一次 SPA，后续分区切换都复用同一页面、缓存和会话，并在每次
切换后等待官方岗位接口响应。跨分区仍强制先复位到根筛选，重复打开同一分区直接复用已验证的响应。

| 渠道与范围 | 旧实现 | 单次 SPA 初始化 | 完整性 |
| --- | ---: | ---: | --- |
| 字节社招 20 页 | 204 秒，1,921 请求，CDP 15.71 MB，Docker 约 18.48 MB | 162 秒，450 请求，CDP 12.53 MB，Docker 约 14.43 MB | 岗位 4,000、集合哈希一致 |
| 字节社招全量 | 64 页，约 28.8 MB Docker 收发（上一日基线） | 64 页，11,641 岗位，约 21.9 MB Docker 收发，连续两轮哈希 `f8301395...` | 完整，无 OOM |
| 字节校招全量 | - | 38 页，7,423 岗位，CDP 11.54 MB，Docker 约 13.34 MB | 完整，哈希 `19d560be...` |

旧全量基线为前一日 11,642 个岗位；候选两轮均为 11,641 且哈希一致，属于官网在不同采集时间发生的
单岗位变化，不是随机漏数。20 页对照的集合哈希完全一致，且分类/城市分区计数和分页元数据均通过。
内存峰值约 1.09 GiB、无 OOM；因此该优化已可用于日常采集。实验脚本现在显式传递并记录
`COLLECTOR_IMAGE`，候选镜像不会被误当成 `latest`。

### 2026-08-20 蚂蚁招聘绕过 SPA 初始化

蚂蚁社招页面的岗位和分类数据来自公开 POST 接口。请求级实验确认，接口只需要同源的公开
`ctoken` cookie 和查询参数，不需要执行招聘 SPA。连接器现在只打开同源的轻量 `robots.txt` 文本页建立
页面上下文，然后使用页面内 `fetch` 调用官方分类与岗位接口；这样既不加载两套约 2 MB 的前端脚本，
又让 API 请求继续进入 CDP 网络指标。分类目录和每页原始 JSON 仍然保存，岗位总数、页大小、当前页和
唯一岗位集合仍逐项校验。

| 范围 | SPA 初始化基线 | 页面内官方 API | 结果 |
| --- | ---: | ---: | --- |
| 蚂蚁社招 20 页 | 970 岗位，CDP 4.82 MB，Docker 约 7.1-7.9 MB | 969 岗位，CDP 1.02 MB，Docker 1.03 MB | 候选轮次按 20 页正常返回，差异来自官网实时岗位变化 |
| 蚂蚁社招全量 A | - | 1,166 岗位，48 页，CDP 2.28 MB，Docker 约 2.51 MB，170 秒 | 完整，哈希 `3e555c00...`，无失败请求、无 OOM |
| 蚂蚁社招全量 B | - | 1,166 岗位，72 页，CDP 3.41 MB，Docker 约 3.68 MB，233 秒 | 冲突后自动重抓，哈希仍为 `3e555c00...` |

全量轮次超过理论 24 页，是因为官网在采集期间岗位集合或正文发生变化。连接器会丢弃发生版本冲突
的尝试并重新抓取，或按多轮唯一并集直至收敛；不完整、总数不一致或超过重试上限时不会写入每日权威
快照。请求间隔仍保持默认 1.5 秒；一次 0.5 秒间隔实验虽然完整，但没有在动态官网上稳定缩短墙钟
时间，因此不改变默认值。

同为 20 页时，这次优化把蚂蚁的 CDP 接收量降低约 79%，Docker 收发量降低约 86%；完整轮次即使因
官网变化重抓到 72 页，Docker 收发仍只有约 3.68 MB。容器内存峰值从约 573 MiB 降到不超过 350 MiB。
指标中的 `fetch` 字节现在包含岗位和分类 API，不再出现“实际有流量但 CDP 为 0”的低估。

2026-08-20 对“列表返回岗位 ID、详情页再加载 JSON”的来源做了请求级探测。360 详情页实际请求
`GET /v2/index/getjobone?id=...`；拼多多详情页实际请求
`POST /api/careers/api/recruit/position/detail`。两个连接器保留一次官网列表页初始化，详情改用同一
浏览器上下文的官方 JSON 接口，继续保存完整详情 payload 并执行列表/详情身份与字段一致性校验。

| 来源与范围 | 旧实现 | 新实现（1.5 秒间隔） | 0.5 秒稳定性实验 | 完整性 |
| --- | ---: | ---: | ---: | --- |
| 360 社招全量 | 约 47 秒，287 请求，物理网卡约 3.03MB | 约 41 秒，12 个浏览器请求，物理网卡约 2.88MB | 17.17 秒、15.53 秒 | 两轮均为 25 岗位、1 页、哈希一致 |
| 拼多多校招全量 | 约 38 秒，937 请求，约 5.20MB CDP | 约 39 秒，53 请求，约 4.73MB CDP | 15.30 秒、14.83 秒 | 两轮均为 22 岗位、3 页、哈希一致 |
| 拼多多实习全量 | 未单独计时 | - | 3.79 秒 | 2 岗位、1 页、完整 |

直连接口由 Playwright `APIRequestContext` 发出，不进入页面 CDP 统计；因此 360 的流量对照使用
`enp0s5` 网卡增量，拼多多表中的 CDP 数字只用于比较被移除的页面附属资源。最终网络账单仍以
Docker `NET I/O` 或虚拟机网卡为准。请求间隔 0.5 秒是配置校验允许的下限，连续完整采集没有出现
HTTP 错误、漏数或哈希漂移，因此只对这两个来源使用 0.5 秒默认值，其他来源继续保持 1.5 秒。

该类优化不能机械套用到所有网站。需要先确认官网页面与 JSON 接口的映射、请求方法、必要请求头和
会话状态，再以岗位数、分页元数据、详情内容和集合哈希做回归。列表接口仍保留官网页面初始化，避免
因缺少会话或前端生成参数而得到空数据或服务端错误。

## Ubuntu 并发矩阵

虚拟机当前真实批次运行时不要做矩阵实验，否则带宽和 CPU/内存数据会被污染。批次结束后，固定
同一组代表来源（默认字节社招、京东社招、网易综合、蚂蚁社招），每一档至少重复两次。字节覆盖
大结果集和反复页面导航，京东/网易覆盖轻量官方接口，蚂蚁覆盖约 800 MiB 的重型浏览器上界：

仓库中的 `deploy/run-concurrency-benchmark.sh` 会执行固定来源的 dry-run，不写 PostgreSQL 或原始
数据，并在输出目录保存每个来源的 JSONL、退出码、墙钟和 Docker 资源采样。可在 Ubuntu 上按档位
运行：

```bash
BENCHMARK_PARALLEL=1 deploy/run-concurrency-benchmark.sh
BENCHMARK_PARALLEL=2 deploy/run-concurrency-benchmark.sh
BENCHMARK_PARALLEL=3 deploy/run-concurrency-benchmark.sh
BENCHMARK_PARALLEL=4 deploy/run-concurrency-benchmark.sh
```

默认每个来源最多抓 20 页；要做完整性矩阵可设置 `BENCHMARK_MAX_PAGES=1000`，但耗时和流量会
明显增加。每一档应使用新的 `BENCHMARK_RUN_ID`，不要覆盖之前的输出。
脚本会先检查 `job-market-monitor-collector:latest` 已存在，并使用 `--pull never`；镜像缺失时直接
失败，不会在基准期间拉取镜像或安装 Chromium。

```text
MAX_PARALLEL_SOURCES=1, 2, 3, 4
CRAWL_BLOCK_NONESSENTIAL_RESOURCES=true
CRAWL_BLOCK_SERVICE_WORKERS=true
```

每次记录批次墙钟时间、各来源状态/岗位/页数、输出中的 CDP 网络指标、Docker `stats` 的 CPU/内存
峰值和每个容器 `NET I/O`。每个采集摘要的 `collection_hash` 是按岗位 ID 和内容版本哈希排序得到的
集合指纹，不包含原始岗位内容；不同并发档位应相同。另外执行 `check-schema`、`check-data`，确认
数据库没有唯一键冲突、每日快照数量正确。

默认并发选择规则：所有重复轮次成功、峰值内存不触发 swap/OOM、来源岗位数和完整性校验一致，且
批次墙钟时间有实际改善；否则退回上一档。2 核、约 3.3 GiB 内存的虚拟机以 2 为起点，3 和 4
只有在实测稳定时才考虑，不根据理论 CPU 倍数直接启用。

### 2026-08-19 Ubuntu 完整矩阵结果

环境为 Parallels Ubuntu 26.04、2 vCPU、3.3 GiB 内存。四档都使用相同来源和
`BENCHMARK_MAX_PAGES=1000`，实际均运行到连接器完整性收敛：字节社招 11,642、京东社招 1,731、
网易综合 2,557、蚂蚁社招 1,161。所有轮次的各来源 `collection_hash` 完全一致。

| 并发 | 完整轮次墙钟 | 最低可用内存 | swap in / out | OOM | Docker 接收量 | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 531 秒 | 未采样 | 未采样 | 0 | 约 36.6 MB | 顺序基线 |
| 2 | 317 秒 | 903 MiB | 1.1 / 23.0 MiB | 0 | 约 36.5 MB | 成功 |
| 2（重复） | 335 秒 | 901 MiB | 0.8 / 0 MiB | 0 | 约 35.1 MB | 成功 |
| 3 | 308 秒 | 788 MiB | 4.6 / 88.8 MiB | 0 | 约 35.2 MB | 仅比 p2 快 9 秒 |
| 4 | 326 秒 | 543 MiB | 72.2 / 77.8 MiB | 0 | 约 35.2 MB | 比 p2 首轮更慢 |

swap 数值是 `/proc/vmstat` 的页增量按 4 KiB 页折算，不是实验开始前已经占用的静态 swap。
p2 两次比顺序基线缩短 37% 至 40%；p3 的额外收益只有 2.8%，同时最低可用内存减少约 115 MiB、
swap out 明显增加。p4 已出现约 72 MiB swap in 且速度倒退。最终默认值保持
`MAX_PARALLEL_SOURCES=2`，p3/p4 只用于压力测试，不用于日常调度。

四档 Docker 总接收量基本都在 35 至 37 MB，说明来源级并发没有造成重复抓取或放大总流量；它只会
让同样的流量在更短时间内重叠。日常调度使用 `SOURCE_START_DELAY_SECONDS=3` 错开浏览器启动峰值，
并发 2 也把瞬时带宽上界限制在两个来源。若部署机器带宽比本虚拟机更小，应优先增加启动间隔，
其次才把并发降为 1，不应缩减分页或跳过岗位详情来换速度。

本次完整矩阵的代表轮次中，字节约接收 26 MB、蚂蚁约 7 MB、京东与网易各约 1 MB。总流量的主要
优化点因此不是压缩数据库写入，而是减少浏览器附属资源和官网接口页数。当前实现已经：

1. 通过 CDP 阻止常见图片、字体、音视频和 Service Worker，不使用会关闭 Chromium HTTP 缓存的
   全局 `context.route`。
2. 腾讯、京东、网易、美团、蚂蚁使用官网允许的较大接口页长或收敛轮次，避免大量小分页。
3. 保留岗位 JSON 和完整性对账所需请求；不会为了省流量丢弃详情、城市、类别或官网原始字段。

`failed_request_count` 记录浏览器层所有失败请求，其中包括页面统计、预加载和被页面取消的附属请求，
不能单独作为岗位失败依据。写入条件仍由官网总数、分页行数、唯一岗位集合和连接器完整性校验决定；
任何一个不满足都不会形成权威每日快照。

## 流量口径与镜像隔离验证

Dockerfile 中的 `playwright install --with-deps chromium` 只在镜像构建时执行，会下载 Playwright
浏览器包、headless shell、ffmpeg 以及系统依赖。它不是每日采集步骤。定时脚本会先检查
`job-market-monitor-collector:latest` 已存在，再使用 `docker compose run --pull never`；镜像缺失时直接
记录预检失败，不自动拉取、构建或安装 Chromium。

2026-08-20 在 Ubuntu 虚拟机执行了一次 360 社招单页 dry-run，命令使用上述 `--pull never` 且不写数据库：

| 指标 | 结果 |
| --- | ---: |
| 岗位/页面 | 25 / 1，完整 |
| 采集器 CDP `received_bytes` | 2,512,934 bytes |
| 虚拟机 `enp0s5` RX 增量 | 2,674,609 bytes |
| 虚拟机 `enp0s5` TX 增量 | 353,464 bytes |
| 虚拟机网卡收发合计 | 3,028,073 bytes（约 2.89 MiB） |

运行前后镜像摘要均为 `sha256:84e51cf...`、镜像大小为 595,857,902 bytes；Docker image/builder 事件为空，
镜像内 `/ms-playwright` 已存在（约 984MB，包含 Chromium、headless shell 和 ffmpeg）。因此这次网卡增量
是招聘网站请求及协议开销，不是 Chromium 二进制下载或镜像构建。

以上是三个不同统计层，不能直接相加：采集器字节是浏览器响应体的近似值，虚拟机网卡包含 TCP/TLS、DNS、
请求上传和 Docker 转发开销，宿主机 FlowWatch 中的 Parallels Desktop 则可能聚合整台虚拟机的全部外网流量。
如果同时查看这三者，应以虚拟机网卡或 Docker `NET I/O` 作为本项目网络账单，不能把 Parallels 数字再加一次。
宿主机上其他路径（例如 AutoEmailSender 自带的 `ms-playwright`）出现的 `chrome-headless-shell` 流量，也不能
归因给本项目的 Docker Chromium。

实验脚本现在额外生成：

- `system-stats.tsv`：可用内存、swap 页、OOM 和负载时间序列。
- `system-summary.txt`：最低可用内存、swap in/out 与 OOM 增量。
- `container-peaks.tsv`：每个来源的 CPU、内存峰值和最终 Docker `NET I/O`。

这些文件只保存在运行机器的临时实验目录，不进入 Git，也不包含岗位正文。
